# 平台差异与最小迁移路径

适用：把已经可用的应用迁到小程序、移动端、桌面或另一套渲染框架。目标是保留用户认可的业务结果和关键交互，同时适配真实的平台约束。

## 先读现有实现，再确定适配边界

按任务相关程度核对下面几类差异，记录“可复用 / 需适配 / 需实测”，不要仅列术语：

| 差异 | 要验证的具体问题 |
| --- | --- |
| 编译和模块 | 当前 TypeScript/JavaScript 配置、模块解析、路径别名、依赖是否可在目标运行时编译；需要的 polyfill 或替代库是否支持目标版本 |
| 渲染和样式 | DOM/JSX 是否需要改成目标模板；选择器、布局、字体、单位、图标和暗色机制是否支持；浮层在目标组件树里怎么挂载 |
| 事件和生命周期 | 浏览器事件与目标事件的参数和传播差异；初始化、页面恢复、后台/前台、订阅卸载是否会漏保存或重复操作 |
| 路由和资源 | 页面注册、跳转栈、深链、资源路径、分包和资源体积限制是否影响用户原流程 |
| 身份和访问控制 | 原登录方式是否可复用；新身份怎样映射旧账户；用户隔离和服务端规则是否仍成立 |
| 存储与同步 | localStorage/IndexedDB 与目标存储 API、容量、序列化、离线行为怎样对应；失败是否保留修改；旧记录 ID 和引用是否兼容 |
| 网络与图片 | 请求接口、允许域名、上传/下载、临时文件、压缩/预览的限制；原图引用能否在正确账户下读回 |

读取目标平台官方文档或版本对应源码，只核对当前方案用到的能力。不要沿用历史模板列表、假定某个编译器能处理全部旧代码，或根据模板名称就声称可迁移。

## 选择一条能暴露差异的完整流程

例如目标记录应用：

1. 从原应用导出或构造不含个人数据的小样例，保留稳定 ID、进度、关联目标和一张测试图片。
2. 在独立目标目录实现“列表 → 编辑 → 保存 → 重新打开/重启 → 读取同一记录”。涉及身份和图片时把对应调用接进这一条路径。
3. 对比用户可观察的内容、状态、选中项、计算结果与异常反馈；验证目标编译器及真实运行时允许的操作。
4. 这条路径满足对照要求后再迁移其余页面。失败时修正具体适配点，避免批量搬完后重新修整站。

尽量原样复用日期、统计、收支、目标计算等纯业务模块和相关测试。通过存储、网络、身份、图片等边界适配替换平台能力；不要让页面重新实现一套计算规则。

新平台需要重做界面代码时，保存关键截图/交互描述和源测试作为对照；不要求组件源码相同，但不能静默丢掉自定义类目、关联、删除、刷新恢复等已验收功能。

## 小程序场景的具体边界

React/Next.js 网页迁到微信小程序时，先查当前项目是否已有目标工程与模板选择。没有现成目标工程才比较适合的模板。WXML/WXSS、组件体系、路由、文件接口和平台登录需适配；是否采用跨端框架由当前维护成本和依赖兼容证据决定。

不能把网页的 DOM、Radix Portal、浏览器图片处理、Firebase Web SDK、localStorage/IndexedDB 原封不动视为小程序可用能力；也不能未经验证就宣称都必须换后端。逐个核验实际使用版本和接口，保留原网页及数据结构，落实能通过编译和实际运行的方案。

开发者工具编译通过、模拟器交互通过、真机读取/登录/图片通过是不同证据。真机或账号不可用时说明具体缺口，不承诺完整迁移或自动跨平台同步。
